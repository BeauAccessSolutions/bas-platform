### Original entry

**Independently re-verified against production data and the live pages.** Two distinct defects:

**(a) Representation flags assert an attestation that never happened.** `Apnea Care Inc`
(`a90d64d4-…`) carries `disabled_owned = true, disabled_led = true` in the production database, and
its live provider page reads:

> Disabled-owned (a disabled person owns 51% or more): **Yes (self-attested)**
> Disabled-led (a disabled person holds primary leadership): **Yes (self-attested)**

under a heading stating "These are self-attested — no medical proof is ever required." The seed
record (`research/seed-nys/wny-2026-07c.seed.json`) carries the flag
`disabled_owned_needs_attestation` and the note **"NEEDS OWNER SELF-ATTESTATION AT ONBOARDING."**
The owner never attested.

The nuance the fix depends on: the underlying evidence is **not weak** — it is a federal SBA VetCert
SDVOSB certification (≥51% service-disabled-veteran ownership + day-to-day control, active since
2025-05-21, UEI KGABNQ2V7P35). Under §4 that is the **`sourced`** state, the one state permitted to
carry higher confidence. So the label is wrong in *both* directions: it claims an attestation that
doesn't exist while under-describing evidence that is actually stronger than self-attestation.

This is simultaneously a §2/§4 honest-labeling violation, a §12 violation (self-attestation must come
from the owner), a §6 concern (the platform publicly asserts a named business owner's disability
status without their consent), and a §7 liability exposure — a claim *we* confer carries more
liability than one a user reports.

**Fix.** Either (i) suppress the flags until real owner attestation exists at onboarding, or
(ii) render certification-backed representation in a distinct `sourced` presentation that names the
certification and never says "self-attested". **Do not simply delete the flag** — that discards good
evidence. Audit every seeded listing carrying `disabled_owned`/`disabled_led` against its `_review`
flags; `disabled_owned_needs_attestation` is a machine-readable marker to select on.

**(b) Seeded prose summaries publish accessibility claims outside the attribute system.** Confirmed
in production — `BestSelf Behavioral Health Clinic — Franklin Street`:

> "…with 211WNY listing accessible building, parking, restrooms, and visual emergency alarms."

The importer copies seed prose straight into the public `summary`, which renders with **no validation
state, no last-confirmed date, no dissent path, and no re-verification clock** — the four things §4
exists to attach to exactly this kind of claim. A wheelchair user reading that summary has no way to
know it is an unvalidated third-party directory copy, and time-decay can never expire it.

**Fix.** Strip accessibility assertions from imported summaries, or convert them into individually
sourced attribute claims (which is what the `sourced` state is for). Summaries should describe *what
the place is*, not *how accessible it is* — the attribute list owns that.

**Acceptance:** no public summary asserts an access fact outside the attribute list; no listing reads
"self-attested" without a recorded owner attestation.

Every form POST in production returns `403 Cross-site POST form submissions are forbidden`. The
entire write surface — first report, per-claim confirm, listing submission, accessibility settings,
photo reports, sign-out, and both §6 data-rights doors — has never worked. Production DB confirms:
`confirmations = 0`, `contributors = 0`, `contributor_sessions = 0`; all 73 claims `self_reported`.

**Cause.** `astro.config.mjs` builds `security.allowedDomains` from `process.env.SITE_ORIGINS` at
**build time**. `SITE_ORIGINS` is absent from `.do/app.yaml`, absent from the live spec, and the
`Dockerfile` declares no `ARG SITE_ORIGINS`, so a `BUILD_TIME`-scoped var could not reach
`RUN npm run build` even if one were set. `allowedDomains` resolves to `[]` → Astro distrusts the
forwarded host → computes its origin as `https://localhost` → rejects every browser POST.

**Fix — both halves are required:**

1. `Dockerfile`, in the `builder` stage before `RUN npm run build`:
   ```dockerfile
   ARG SITE_ORIGINS=""
   ENV SITE_ORIGINS=$SITE_ORIGINS
   ```
2. `.do/app.yaml`, under the `web` service, **and applied to the live spec**:
   ```yaml
   - key: SITE_ORIGINS
     scope: BUILD_TIME
     value: "access-atlas-qd464.ondigitalocean.app"
   ```

Do **not** disable `checkOrigin`. With a zero-JS surface no client-token CSRF scheme is possible, so
the origin check is the only CSRF layer that exists.

**Branch from `origin/main`, not from the local checkout** — `fix/ios-safe-area` predates `60a381d`
and building on it would regress the very fix being completed.

**Acceptance:** re-run the 7-endpoint probe against production. `/api/settings` → `303`;
the rest → `303` with an honest gate status (`need_signin`), never `403`. Then walk one real
first-report end to end and confirm a `confirmations` row appears and the claim reads
"1 community confirmation".

### Original entry

purpose is to fail-close a deploy when the DB can't be migrated — written *because* code shipping

⚠️ **Reconcile before applying.** The live spec is authoritative for `KEYCLOAK_ISSUER` (flipped live

## R-5 · P2 · Remove the bucket-listing policy on `evidence` — ⬜ not started

The public `evidence` bucket carries `public read: evidence objects` — `SELECT` to `public` with
`qual: (bucket_id = 'evidence')` on `storage.objects`. Public buckets don't need a listing policy for
object-URL reads. As written, anyone can enumerate every object (`<claimId>/<uuid>.jpg`), yielding a
complete inventory of which claims have evidence and enabling a bulk sweep of every disabled
contributor's submitted photo — a §6 data-minimization regression, even though each individual URL is
intentionally public and each photo is EXIF-stripped.

Dormant only because there are zero photos. **Live once R-1 deploys.**

**Fix.** Drop the broad `SELECT` policy. Verify `/storage/v1/object/public/evidence/<path>` still
serves, and that the anon list endpoint no longer enumerates.
